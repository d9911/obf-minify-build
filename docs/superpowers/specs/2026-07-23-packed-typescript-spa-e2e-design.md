# Packed Vanilla TypeScript SPA E2E Design

## Goal

Prove that the package works as an installed npm artifact in a realistic
browser application. The test must exercise the published CLI, optional
TypeScript integration, hashed cross-file references, browser behavior, and
failure reporting instead of importing unpublished repository internals.

## Scope

The implementation adds a checked-in Vanilla TypeScript SPA fixture and a
browser E2E test. It also fixes reference rewriting required by that fixture:

- static JavaScript module imports and exports;
- dynamic `import()` expressions with string-literal specifiers;
- CSS `url()` references;
- CSS `@import` references;
- existing HTML `src` and `href` references.

The published package keeps zero runtime dependencies. TypeScript remains an
optional peer dependency. Browser automation is development-only.

This work does not add a framework, bundler, development server, source maps,
arbitrary JavaScript expression analysis, or remote URL processing.

## Real-world fixture

`test/fixtures/real-world-app` represents a small consumer project rather than
an internal unit-test input. It contains:

- an HTML entry page;
- several TypeScript ES modules;
- a static module import and a literal dynamic import;
- CSS split across files with `@import` and `url()`;
- an image referenced from HTML;
- JSON loaded with `fetch`;
- a form and counter driven by DOM events;
- state persisted to and restored from `localStorage`.

The fixture's source references are deliberately relative and include query or
fragment suffixes where useful. The output must contain hashed local
JavaScript, CSS, and image files. No emitted reference may point to a removed
unhashed filename.

## Package-consumer flow

The E2E test performs these steps:

1. Run `npm pack` in the package repository and capture the generated tarball.
2. Copy the fixture into a fresh temporary consumer directory.
3. Install the tarball into that consumer project with npm.
4. Install or provide TypeScript as the consumer's development dependency.
5. Invoke the CLI from the consumer project's local `node_modules/.bin`.
6. Serve the generated output with a zero-dependency Node.js HTTP server bound
   to loopback on an ephemeral port.
7. Open the application in a real headless browser.
8. Exercise user-visible behavior and inspect browser/runtime failures.
9. Stop the server and remove temporary artifacts, including the tarball, in a
   `finally` cleanup path.

The test must not resolve the CLI or library directly from the source checkout
after installation. This ensures that missing `files`, `bin`, `exports`, or
package metadata are observable.

## Reference rewriting

Hashing remains a two-phase operation:

1. transform and write output files;
2. derive final hashed names and rewrite local references to those names.

Reference resolution is relative to the file containing the reference. Root
paths remain root paths. Query strings and fragments are preserved. Remote
URLs, protocol-relative URLs, `data:`, `node:`, and fragment-only references
remain unchanged.

JavaScript rewriting supports only quoted string-literal specifiers in:

- `import ... from "..."`;
- `export ... from "..."`;
- side-effect imports such as `import "./setup.js"`;
- dynamic imports such as `import("./feature.js")`.

Computed dynamic imports are left unchanged and produce a warning because
their target cannot be determined safely without executing code.

CSS rewriting supports quoted or unquoted `url()` and quoted `@import`.
Whitespace and quote style may be normalized by the existing transform.
References inside comments and strings unrelated to these constructs must not
be rewritten.

Reference rewriting must use the package's native lexer/token-aware utilities
where JavaScript ambiguity would make a regular expression unsafe.

## Browser assertions

The browser test fails on:

- any same-origin response with status `400` or higher;
- an uncaught page error;
- a console error produced by the application;
- a missing expected hashed file;
- an output reference to a removed unhashed local asset.

It also verifies:

- the initial JSON data is rendered;
- the counter changes after a click;
- the form accepts valid input and updates visible state;
- the dynamic module loads and changes the page;
- the CSS-imported rule and background image are applied;
- the HTML image loads with non-zero intrinsic dimensions;
- state survives a page reload through `localStorage`.

Expected browser diagnostics generated by the test runner itself may be
filtered only by an explicit, narrowly matched allow-list documented in the
test.

## Additional installation scenarios

Two package-level scenarios remain separate from the browser SPA:

- a JavaScript-only consumer installs and builds successfully without
  TypeScript;
- a consumer containing `.ts` files but no TypeScript installation fails with
  a clear message containing `npm install --save-dev typescript`.

These scenarios also install from the packed tarball. They do not require a
browser because their acceptance criteria concern installation and CLI error
handling.

## Test commands

`npm run test:e2e` runs the packed SPA browser scenario independently.
`npm test` includes it so the release gate cannot pass while the realistic
consumer is broken. Existing focused commands such as `npm run test:package`
remain available.

The E2E runner uses Node.js test APIs and a development-only browser automation
tool. The fixture application itself has no runtime library dependency other
than the package under test and the optional TypeScript peer used at build
time.

## Reliability and cleanup

The server listens on `127.0.0.1` with an operating-system-assigned port.
Readiness is determined from the server's listening event, not a fixed delay.
All child processes are invoked with argument arrays and `shell: false`.
Temporary paths are created under the operating system's temporary directory.
Cleanup runs after success and failure.

Assertions report the requested URL, status, browser error, or unresolved
reference so failures can be reproduced without guessing.

## Acceptance criteria

The change is complete when:

- the packed tarball installs in an isolated consumer;
- the browser SPA passes every functional and resource assertion;
- hashed JS module and CSS asset references resolve correctly;
- JS-only and missing-TypeScript package scenarios behave as specified;
- `npm test`, `npm run test:e2e`, `npm run lint`, `npm audit`, and
  `npm pack --dry-run` pass;
- `npm ls --omit=dev --omit=optional --depth=0` reports no runtime dependency;
- package documentation explains the realistic E2E command;
- no remote push, tag, npm publication, or pull request is performed.
